# Table-driven CRC32C

Date: 2026-10-03. Host: Apple M1 Max, 64 GiB RAM, APFS, macOS 26.6.2.
This is a local optimization A/B and one pinned RocksDB diagnostic, not a
cross-platform release claim.

## Change

A two-second process sample of W2 identified the portable bit-at-a-time CRC32C
loop as the largest CPU component in WAL encoding. Each byte previously
required eight polynomial steps, and WAL encoding checksummed the large record
payload twice.

The candidate builds a 256-entry lookup table at compile time from the existing
Castagnoli polynomial and performs one table step per byte. It uses safe Rust,
adds no dependency, and does not change the checksum definition, WAL encoding,
page encoding, public API, or database format.

The preregistered W2 acceptance gate required at least 10% higher median active
throughput, no more than 2% higher median maximum RSS, and identical persisted
bytes and logical contents.

## Method

- Baseline: `2c9f9c8`.
- Candidate: the isolated `checksum.rs` diff recorded in the raw manifests.
- Dataset: 1,000,000 entries, 16-byte keys, 100-byte values.
- Batch: 10,000 mutations per synchronous commit.
- Durable write buffer: 64 MiB.
- Cache: 65,536 decoded pages.
- Workloads: W1 sequential durable load and W2 random durable load.
- One warm-up process followed by five measured processes per variant and
  workload.
- Measured processes were alternated and each used a new database.

Raw commands, stdout, stderr, process-resource reports, executable hashes, and

## Causal A/B results

| Workload and metric | Baseline | Candidate | Change |
| --- | ---: | ---: | ---: |
| W1 median throughput | 243,801 ops/s | 329,728 ops/s | +35.25% |
| W1 median commit time | 3.775 s | 2.710 s | -28.22% |
| W1 median sync time | 2.225 s | 1.377 s | -38.10% |
| W1 median maximum RSS | 171,442,176 B | 171,278,336 B | -0.10% |
| W2 median throughput | 194,322 ops/s | 257,074 ops/s | +32.29% |
| W2 median commit time | 4.780 s | 3.524 s | -26.27% |
| W2 median sync time | 2.250 s | 1.429 s | -36.48% |
| W2 median maximum RSS | 233,668,608 B | 233,783,296 B | +0.05% |

All five candidate W1 samples exceeded every baseline W1 sample. All five
candidate W2 samples exceeded every baseline W2 sample. The candidate passed
the preregistered W2 gate.

Every baseline and candidate run reported the same logical SHA-256, storage
bytes, and 1.651 database write amplification. The main-file hashes were
identical across both variants for each workload, as were their WAL hashes.
This establishes byte-for-byte format compatibility for the measured data.

## Current RocksDB W2 diagnostic

The repository comparison runner then alternated the candidate with the pinned
official RocksDB 11.8.1 `db_bench` executable. Both engines used synchronous
WAL-backed commits, 100-byte values, 10,000-mutation batches, one warm-up, and
five measured processes.

| Metric | WSLDB | RocksDB 11.8.1 |
| --- | ---: | ---: |
| Median active throughput | 270,075 ops/s | 586,696 ops/s |
| Median maximum RSS | 233,848,832 B | 114,835,456 B |
| Median whole-process wall time | 4.75 s | 7.01 s |
| Logical storage bytes | 123,449,976 B | 121,951,145 B median |

RocksDB remains 2.17 times faster in the W2 active interval and WSLDB uses 2.04
times its median whole-process peak RSS. WSLDB's shorter whole-process time is
not treated as a throughput win: its final state includes a recoverable WAL
tail, while the RocksDB runner explicitly flushes and waits for compaction.

## Correctness verification

The table implementation matches the previous bitwise implementation for every
prefix length of a deterministic 512-byte corpus and matches the standard
`123456789` CRC32C check value. The following checks passed:

- `cargo fmt --all -- --check`
- `cargo test --all-targets --all-features`
- `cargo clippy --all-targets --all-features -- -D warnings`
- `cargo check --all-targets --all-features`
- `git diff --check`

The opt-in release corruption matrix also passed 100,000 deterministic
main-file mutations and 100,000 deterministic WAL mutations. Every accepted
input matched a known complete state; all other inputs failed closed. Both
tests passed with zero unknown accepted states in 3,712.59 seconds. This finite
APFS result is not a power-loss or cross-platform claim.
